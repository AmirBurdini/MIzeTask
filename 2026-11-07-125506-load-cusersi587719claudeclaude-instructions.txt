❯ as for your question about request limit, build on the following idea (and    
  show its flaws), for each supplierId start a 100 counter, for each incoming   
  request(accepted or rejected) decrement by 1, and increment 1 every 10/6      
  seconds, is this sound reasonable?                                            

● Yes, it's reasonable. What you've described is a token bucket with a capacity
  of 100 and a refill of 100 per 60 seconds (one token every 1.667 seconds).
  It's a standard design and it works across instances. But it doesn't match the
  literal spec in a few ways.

  Flaws against the spec

  1. It allows about 200 requests in a 60-second window, not 100.
     - A supplier sends 100 requests at t=0 and drains the bucket. By t≈59s it
       has refilled about 100 tokens and sends 100 more.
     - That's about 200 accepted requests inside one rolling 60-second window.
     - The spec says more than 100 in any rolling 60 seconds gets rejected.
  2. It under-allows after a pause. A supplier sends 100 requests, waits 30
     seconds, and sends 100 more. The spec says the second batch is rejected,
     because the window still holds 100 requests. The bucket would accept about
     50 of them, so it is too lenient in the first case and a different shape in
     the second.
  3. Debt is unbounded if rejected requests keep decrementing.
     - A supplier that sends 1,000 requests in a burst ends at about -900.
     - It then stays locked out for about 25 minutes (900 ÷ 0.6 tokens per
       second), not 60 seconds.
     - If you want "reject until the window clears", clamp the floor. A floor of
       -100 caps the lockout at about 170 seconds. A floor of 0 means rejected
       requests cost nothing.
  4. A timer-based refill breaks with several instances. "Increment every 10/6
     seconds" has to be computed lazily. Store tokens and lastRefillUtc, and on
     each request add elapsed × 0.6. A background timer on every instance would
     multiply the refill.
  5. The read-modify-write has to be atomic. Two instances reading 1 token will
     both accept. In SQLite this means one transaction that takes the write lock
     up front (BEGIN IMMEDIATE) or a single UPDATE ... RETURNING. It's easy to
     get right, but easy to get wrong with a plain read followed by a write.
  6. It uses fractional state. Store milliseconds or a double, and compare >= 1.
     Rounding to whole tokens causes drift.

  What it does well
  - It's one row per supplier, with no per-request log and no pruning.
  - Writes are cheap and constant-time.
  - Counting rejected requests matches "a supplier sends more than 100", which
    is a defensible reading of the spec.

  The alternative is a sliding-window log: one row per request timestamp. For
  each request, count the rows in the last 60 seconds, reject if there are 100
  or more, and otherwise insert. This matches the spec exactly and the lockout
  is naturally bounded at 60 seconds. The costs are one insert per request and a
  periodic prune.

  My recommendation is the sliding-window log, because "any rolling 60-second
  window" is an exact guarantee and the volume is small. The token bucket is the
  better production choice at high scale.

  Do you want an exact 100-per-rolling-60-seconds guarantee, or would you accept
  the token bucket's burst of up to about 200 for its constant-size state?

❯ would your solution fit webhook from multi instance services? what about      
  concurenncy issues?                                                           

● Short answer: the design is correct for multiple instances, but SQLite limits
  where those instances can run.

  Where it fits
  - All the state lives in the database: the request log, the reservations
    table, and the counters. Nothing sits in process memory, so any instance can
    handle any request.
  - SQLite works for multiple instances only if they are processes on one 
    machine sharing the same database file. Its locking is unreliable on network
    file systems, and it can't be reached across hosts.
  - If the instances are on different servers, you need a networked database
    such as SQL Server or Postgres. The SQL would barely change, except for the
    upsert syntax and using database-side time.
  - For the exercise, I'd treat "multiple instances" as several processes on one
    file and state that in the README as an assumption.

  Concurrency problems, and how I'd handle each

  1. Throttle check-then-insert race.
     - Two requests both count 99 and both insert, which gives 101.
     - The fix is to make the count and the insert one atomic step. That means
       either a single conditional statement (INSERT ... WHERE (SELECT COUNT(*) 
       ...) < 100) or a transaction that takes the write lock up front.
     - The default deferred transaction in SQLite is a trap here. It reads
       first, then tries to upgrade to a write, and in WAL mode that can fail
       with SQLITE_BUSY without being retried by the busy timeout.
  2. Duplicate or concurrent identical requests.
     - A unique key on (supplierId, reservationId) plus INSERT ... ON CONFLICT 
       DO UPDATE ... WHERE <details differ> handles this.
     - The affected-row count and RETURNING tell me whether the result was
       created, updated, or unchanged. Doing a SELECT first and then a write
       would race.
  3. Stale or out-of-order updates. The upsert's WHERE clause can also require
     the incoming updatedAtUtc to be at least the stored one. Without it, a late
     retry could overwrite newer data. This depends on what we decide for
     question 8 in my earlier list.
  4. Stats counters.
     - They need to be incremented in SQL (n = n + 1), in the same transaction
       as the decision.
     - Reading a counter and writing it back loses updates. A separate
       transaction can leave the counters out of step with what actually
       happened.
  5. SQLite's single writer.
     - Concurrent writes queue behind one lock.
     - I'd enable WAL mode and set a busy timeout. Throughput is limited, but
       100 requests a minute per supplier is far below that limit.
     - Putting throttle, upsert, and counters in one short transaction per
       request keeps the reasoning simple and keeps the three consistent.
  6. Clock skew.
     - On one machine every instance shares the clock, so there's no issue.
     - Across hosts, the window would break if each instance used its own clock.
       The database should supply the time.
     - Either way I'll inject a clock for tests.
  7. Supplier retries. Our dedup makes retries safe. If we commit but the
     response is lost, the retry returns "unchanged". It also counts toward the
     rate limit, which seems right.
  8. Cleanup. The request log grows, so it needs periodic pruning of rows older
     than 60 seconds. Pruning has to be safe under concurrent use too.

  How I'd prove it: a test that fires 200 or more parallel requests at one
  supplier, through several separate app instances on one file, and asserts
  exactly 100 accepted. That is the test most likely to catch a
  check-then-insert race.

  Are you comfortable treating "multi-instance" as several processes on one
  shared SQLite file, with the networked-database limitation documented in the
  README?

  The Mize directory is greenfield. It contains only this spec, so there is no
  existing table or schema to match. Questions ranked by importance:

  1. **What is the request body, and how many reservations does one request
  carry?**
     - The spec lists fields (`supplierId`, `reservationId`, `roomId`,
  `checkIn`, `checkOut`, `price`, `updatedAtUtc`) but gives no JSON shape,
  casing or types. It also doesn't say whether the endpoint takes one
  reservation or a batch.
     - It doesn't say whether `supplierId` is in the body, a header or the
  route.
     - Why it matters: this is the contract everything else hangs on. A batch
  would break the single status per response (201, `created` and so on), the
  "every request counts" throttle, and the per-request single transaction. The
  `supplierId` location decides how the throttle identifies the caller.
     - My default would be one reservation per request, with a flat JSON body
  containing `supplierId`. A wrong guess means rewriting the controller,
  response model, tests and all counters.

  2. **Does a request rejected with 429 also add a row to the throttle log?**
     - The spec says "every request counts toward the window, including
  rejected". It then lists invalid, duplicate and stale as examples, and
  separately says the 429 increments the throttled counter.
     - If 429s are logged, a supplier that keeps hammering never recovers. The
  window keeps sliding forward, and `Retry-After` and the "window clears" test
  behave very differently.
     - If they aren't logged, the window only counts accepted-for-processing
  requests.
     - Why it matters: this changes the atomic conditional-insert SQL, how
  `Retry-After` is computed, and the throttle tests.

  3. **Which supplier bucket does a request fall into when `supplierId` is
  missing or blank?**
     - Throttle runs before validate, but the blank-`supplierId` check lives in
  validation. A request with no supplier id has no throttle key.
     - Options are to skip throttling, throttle under a shared "unknown" key, or
  validate the supplier id before the throttle.
     - Why it matters: it affects pipeline order, the 400-versus-429 precedence,
  and whether anonymous traffic can bypass the throttle (an anti-goal).

  4. **What are the types and formats of the date and price fields?**
     - It is unclear whether `checkIn`/`checkOut` are dates or datetimes. It is
  also unclear whether `updatedAtUtc` may carry an offset, and what happens to a
  non-UTC or offset-less value.
     - The spec doesn't say whether `price` is decimal, and in SQLite it would
  need to be stored as REAL or integer cents.
     - Why it matters: the `ON CONFLICT ... WHERE incoming not older and details
  differ` logic compares these values inside SQL. Text timestamps must be
  normalised to one sortable format, and float equality on price must be exact,
  or "unchanged" versus "updated" misfires. The spec leaves column types to the
  builder but gives none of the input types.

  5. **How should malformed input be handled, such as unparseable JSON, a
  missing `updatedAtUtc`, or a wrong type?**

❯ what happens inside GetAsync if its given non-existing supplierId             

● It returns zeroes and changes nothing. In Stats/StatsQuery.cs, GetAsync does
  the following:

  1. It opens a read-only connection, so it can't write anything.
  2. It runs SELECT ingested, throttled FROM supplier_stats WHERE supplier_id = 
     @supplierId with the ID as a parameter.
  3. QuerySingleOrDefaultAsync<CounterRow> returns null when no row matches. It
     does not throw.
  4. row?.Ingested ?? 0 and row?.Throttled ?? 0 then turn that null into 0 and
     0, and the method returns SupplierStats(supplierId, 0, 0).

  The controller turns that into a 200 with
  {"supplierId":"nobody","ingested":0,"throttled":0}. I checked this against the
  running app earlier with the supplier ID nobody.

  Side effects
  - A lookup never creates a row. A stats call for a made-up supplier leaves the
    database unchanged. The supplier_stats row is created only when ingest
    first counts something for that supplier.
  - A supplier whose requests were all invalid, duplicates, or stale also has no
    row. Those outcomes add nothing to either counter, so the supplier looks
    the same as an unknown one. Both return zeroes.
  - The lookup is case-sensitive. ACME and acme are different suppliers, and
    ACME returned zeroes in my run.
  - The "unknown supplier returns zeroes" rule is your decision, not a bug. The
    cost is that a typo in the supplier ID looks identical to a supplier with no
    traffic. If you'd rather return 404 for suppliers with no request history,
    that would be a separate change, and it would also need the throttle log or
    a row created on first contact.

  The one thing GetAsync doesn't handle is a missing database file or missing
  table. StatsController checks for the file first and returns the 503. A
  missing table would surface as a 500 until the error mapping in Phase 4 turns
  it into something cleaner.
